# Independent test coverage and parallelism assessment

The best immediate changes are to run engine-independent checks once, consolidate one demonstrated duplicate regression, and shard browser suites onto separate runners while keeping one suite worker inside each shard. Raising same-machine browser concurrency has less supporting evidence. The current suite contains useful rendering, interaction and accessibility coverage that must survive this work.

This assessment answers assignments 11037 and 11038. It examines published documentation commit `8d8430a9f9cab57694856b3655616f8df1ccae16` in the shared audit worktree. Verification owns only this document. The lead's existing RELEASING.md edit and other contributors' documents remain untouched. This review read source, retained release records and Git history; it ran no tests, browser processes, build generators or live release queries. Official GitHub documentation was consulted for proposed workflow semantics. Implementation owns the exhaustive inventory; Build owns timing and benchmark arithmetic.

## What the matrix currently measures

The baseline has 192 top-level `tests/*.test.js` entries. `tests/run.js:88-119` discovers and sorts every entry, then repeats it for each requested engine. CI runs readable Chromium, Firefox and WebKit plus minified Chromium, producing 768 top-level invocations. This count includes nested Node test wrappers and one entirely browser-independent generator check. It is not a count of 768 independent product requirements.

The four browser/form combinations have legitimate differences. `tests/lib.js:25-49` routes readable asset URLs to minified copies; browser behavior remains worth checking against the delivered minified files. CSS selector parsing, layout, native controls, focus, mutation delivery and media handling can differ across engines. Checking source freshness alone does not replace these measurements.

## Diagnostic code and apparent duplication

The normal runner discovers only top-level `.test.js` files. The capture, compare, bevel/runtime/behavior review utilities under `tests/skins/` are not automatically multiplied by the browser matrix. Removing those retained diagnostic tools would not speed `node tests/run.js`. Keep them outside the default gate and preserve their historical evidence.

Names alone are insufficient grounds for removal. `tests/pinned-section-mockup.test.js` opens a mockup but checks restored preferences, pin/window associations and popup interactions. `tests/window-selector-parity.test.js` reconstructs old selector rules, but it also compares actual match sets and computed layout through many DOM permutations. That is browser behavior, not merely a source-string test. Retain it until a concrete retained test covers those permutations. Gel and Glaze preview suites exercise different skins; the material suite covers matte, ink, alloy, alloy-bold and glass, so it is not their replacement. A shared parameterized Gel/Glaze harness can reduce maintenance while retaining both skins and all assertions; it does not automatically reduce runtime.

`tests/skins.test.js:4-5` hides seven browser test files behind a single serial Node test invocation. `tests/palette-themes.test.js` similarly hides browser and static work. Exposing those existing child files as explicit scheduling units can reduce the longest-shard floor without increasing browser concurrency on a runner. Each child needs an explicit engine/form assignment and separate result identity. Preserve nested assertions and failure propagation; do not report a wrapper passing after silently dropping a child.

## Why jobs=1 exists and what sharding changes

Commit `02d2ae22fb9e093b12a6151b4b81633480f82997` introduced parallel suite workers on 1 October. The current runner still defaults to half the logical processor count, capped at eight. Commit `e329c43c51c4a19df35181f5a9421219fd48c864` explicitly added `PUDL_JOBS=1` to CI on 8 November.

`docs/RELEASE-0.105.0.md:15-17,31` records why release execution was serialized. Parallel WebKit attempts produced tooltip/focus and wheel-scroll failures; focused serial checks did not reproduce them. The record leaves their causes unassigned. It describes one suite worker per engine as removal of concurrent browser activity as a variable. It does not prove a product dependency between top-level suites or establish that concurrency caused those failures.

Separate GitHub-runner shards retain that one-worker condition within each runner. They change suite grouping and predecessor history, so validate the proposed schedule rather than claiming it is identical to the old serial history. No evidence here supports requiring Chromium, Firefox and WebKit to wait for one another: baseline CI already uses separate runner jobs. Build should compare two and four shards using retained durations and setup overhead; this document does not infer a speed ratio from worker counts.

The following isolation constraints govern the proposed schedule:

- Each shard needs its own checkout, server and new output root. Separate runners naturally isolate the default port 8765. Two local runner processes need distinct PUDL_PORT and output roots; the runner does not allocate ports automatically.
- `tests/run.js:64-72` isolates suite screenshots beneath engine/suite directories when PUDL_RUN_OUTPUT is set. Nested build tests honor PUDL_OUTPUT_DIR, but their output names can collide if the same wrapper is invoked twice into one root. Include form and shard identity in roots and artifact names.
- Keep generation in check mode while browser shards consume assets. The default modes of tokens, palettes, skins and minifier write generated files; never race them against tests in one checkout.
- Each suite generally launches its own browser and isolated contexts. This supports sharding, but does not prove absence of resource sensitivity or complete descendant cleanup. The outer timeout calls child.kill in `tests/run.js:77`; that line alone is not a process-tree cleanup proof. Separate runner isolation limits cross-shard exposure without repairing that historical limitation.
- Set PUDL_MIN to `1` for minified runs and leave it unset for readable runs. Several nested skin files use truthiness while tests/lib.js uses equality to `1`, so setting the readable flag to the string `0` selects inconsistent assets. A benchmark must not accidentally compare different inputs.

## Required workflow summary

A stable required summary can reject incomplete sharding, provided it checks evidence completeness rather than counting green jobs. GitHub documents that failed or skipped dependencies skip downstream jobs unless overridden; use an unconditional dependency summary and explicitly require successful prerequisites. Matrix output names must also be unique because completion order is unspecified. These constraints come from the official [job dependency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs) and [workflow matrix output documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

The summary should enforce the following conditions using the existing small result JSON format plus explicit shard membership, rather than creating another release framework:

1. Derive the required obligation set from the checked-out test inventory and explicit static/browser routing. Bind checkout identity, engine/form, shard count and scheduling map. Require exactly the expected shard identities and their artifacts; reject missing, duplicate, unknown or empty assignments.
2. Compare every shard's actual rows against its assigned exact filenames. Then require a disjoint union equal to the complete expected engine/form obligation set. Correct row counts alone do not reject one omitted suite paired with a duplicated suite.
3. Preserve actual process status, timeout and printed-failure rejection through suiteResult. Validate each result's schema and exact engine/form, with no coercion of missing/null exits to success. A nested wrapper needs its complete required child outcomes as well.
4. Require fonts, generation/freshness, unit checks and all browser shards to succeed. Always upload available failure evidence, but never turn upload success into test acceptance. Reject missing result/log artifacts, skipped prerequisites, cancellation, malformed JSON or an unstarted suite.
5. Give artifacts distinct engine/form/shard names and keep independent evidence from separate runs/attempts separate. Prevent a shared matrix output key from overwriting earlier shard evidence. Preserve failed logs rather than overwriting them with a later run.

There is a concrete baseline hole to close when adding shards: `tests/run.js:88-120` permits an empty filtered suite list, starts zero workers and exits successfully with zero results. A substring filter can also select multiple unintended suites. Shard selection must be exact, validated and nonempty. The summary must reject zero rows even if the runner returned zero. Validate missing/duplicate shards, a skipped dependency, wrong engine/form, one omitted-and-duplicated suite, an empty selection and a printed FAIL with exit zero before relying on the summary. These controls can use small synthetic result fixtures; a 768-case matrix is unnecessary to prove the summary's set logic.

## Recommendation to the lead

Implement the token/static extraction and duplicate-repro consolidation with explicit retained coverage first. Add exact shard selection and a rejecting workflow summary, then benchmark isolated-runner sharding with one suite worker in each shard. Split the nested skins scheduling boundary if retained timings show it dominates; preserve all child obligations. Keep current browser/form breadth until a separate coverage argument justifies reducing it. The available evidence supports reducing repeated static work and coordination, but does not justify dropping Firefox/WebKit, replacing minified behavior with a freshness check, weakening waits or timeouts, or claiming historical failures explained.
