# Test and release speed audit

## Findings and changes

The baseline contains 192 top-level suites, repeated in four browser/form combinations for 768 invocations. Source inspection classifies 184 as browser behavior, four as mixed static/browser checks, two as nested browser wrappers, one as a wholly static check and one as a duplicate diagnostic. Twelve nested build files were also inventoried. These counts describe scheduling units, not independent product requirements or individual assertions. The [complete inventory](test-suite-inventory-2026-11-20.md) maps every suite to its useful coverage.

The audit found one demonstrated duplicate browser regression, not grounds to discard a large fraction of the suite. The stale-picker diagnostic duplicates a stronger existing activation check and is now opt-in. The wholly static token check and repeated pure palette calculations run once in the static gate. Browser rendering, interaction, native keyboard behavior, accessibility and minified delivery checks remain. The new browser inventory is 190 suites in each of four forms, or 760 original outcomes; token freshness and palette math remain separately required. Other mixed suites contain pure assertions that can be extracted, but their rendered cases have not been dropped.

The main runtime improvement is two isolated CI runners per browser/form, with one suite at a time inside each shard. Serial execution was introduced after unexplained parallel WebKit failures, so same-machine concurrency is not being raised on that evidence. Exact shard identity and original-result union checks prevent an omitted or duplicated suite from looking green. Static/font success remains required. The local static gate passes all 25 Node cases plus token and palette freshness checks. Independent source review is clean, including negative completeness controls and the final release-instruction corrections. Actual hosted timing and full browser validation are still pending at this revision.

The [retained timing assessment](test-runtime-assessment-2026-11-20.md) measures a 20m20s WebKit critical job in the prior documentation run. Simple two-way name partitioning predicts roughly 10m45s including observed setup overhead. That is a scheduling estimate, not a measured speedup. Four shards were considered but repeat more installation work and have less incremental benefit. No new timing database, native process framework or broad diagnostic run was needed for this choice.

The [independent coverage assessment](test-coverage-assessment-2026-11-20.md) identifies further consolidation candidates and the proof each must retain. Historical capture tools outside top-level discovery do not run in the normal suite, so deleting them would not speed it. The release instructions now treat the original requested task as authority for necessary intermediate work and reuse accepted evidence when only a tag label or README receipt changes. No historical release result is rewritten.

Release instructions also compute README distribution integrity values from final local bytes before the release commit. The post-publication anonymous/CDN comparison still has to prove those exact expected bytes. This removes the normal second README commit and its extra browser-matrix trigger without treating public availability as proved early. The tag no longer triggers another identical full matrix; its commit/input binding, object and public artifact checks remain required. PR/main changed-input validation remains in place.
