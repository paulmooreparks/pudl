# Ribbon startup with a launcher identity

Status: research proposal for a product decision. No implementation or rendered mockup is approved by this record. No product source, tests, generated files or host files changed. The inspected distribution is PUDL 0.109.0, accepted tree 40559cb2f80a8a8ac1942727ab3b0b2c5b6075f0. The research branch is research/ribbon-launcher-startup-20261126.

## Cause and current contract

PUDL remembers ribbon versus menu mode in localStorage, keyed by the bar's accessible label or pathname. It remembers tab selection only within the current page session. A new selection prefers the front application's first eligible title when present, otherwise the first eligible host title. A remembered selection remains eligible while its label exists. Application composition combines the titles on the host side with the identity first. See dist/pudl-menubar.js:1867-1910 and :1941-1973.

The launcher-backed identity has two inconsistent roles. It remains eligible for ribbon selection because hasTools excludes Pins and aggregate menu controls but does not require renderable commands or exclude the launcher. The initial selection can therefore choose it. Yet activating the identity opens the launcher through requestLauncher or its native popover binding before the normal ribbon selection path. See dist/pudl-menubar.js:89-105, :1422-1435, :1623-1631 and :1959-1963.

The ribbon toolbar is generated from the selected title's menu items through displayItems and ribbonGroups. It never reads the launcher header or catalog. An eligible title with no command groups produces an empty toolbar while ribbon mode leaves the strip visible. The header buttons are not missing or waiting to paint; they belong to a different surface. See dist/pudl-menubar.js:422-428 and :1975-2052.

The host source report confirms PUDL 0.109.0 is unmodified in the installed fork at 94dc0386, based on Dinah dd008d07. The main-window menubar opts into both data-menubar-launcher and data-menubar-ribbon. The host supplies no start-tab or ribbon-mode override. Its separate document window uses application composition without a launcher. The empty launcher identity strip is a shared integration gap under this supported host configuration. It is not evidence of a host rendering failure. These are source and install-record facts reported by the host lead; this research did not inspect customer content or a running customer window.

Show as ribbon is a stateful toggle with a constant visible label, tooltip and accessible name. aria-pressed=true means ribbon mode, and false means menus. The label does not change to Show menus. A visible generated ribbon strip corresponds to ribbon-on in the shared source; the words alone cannot establish the state from a picture. At narrow widths the bar folds and hides the toggle while retaining the preference. See dist/pudl-menubar.js:1877-1915 and :1980-1989, and docs/proposals/command-bar-and-ribbon.md.

## Reusing launcher actions

The host lead confirms that Settings, Exit and the fork's Updates are registered commands. Settings and Exit have static header buttons whose delegated data-cmd activation and disabled states use dinahCommands. Updates is a fork-specific launcher command projected by drawLauncher from registry rows. Labels and glyphs currently come partly from static markup and partly from those registry descriptors. The host can expose the same operations through a second rendering, provided both views share the command executor, current availability and unsaved-work guards. The ordinary Dinah host has no Updates row, so it must not acquire a meaningless placeholder.

The launcher header should retain its actions when a ribbon projection is present. Its panel still needs to work in menu mode, narrow mode and pinned presentation. Both copies represent the same commands; they do not own separate application state. At a pinned launcher and matching ribbon row, both views may be visible, which should be shown in the approval mockup. Pin, Close and Size are launcher-local presentation controls and do not belong in the projected ribbon action set.

Moving the existing header nodes would remove controls from the launcher. Cloning them does not preserve host event ownership or establish state synchronization. The shared launcher also retains one root, reparents it between popup and pane and delegates its local controls within that root. A projection should consume explicit command declarations and render fresh controls, rather than inspect arbitrary header DOM or forward a synthetic click through the identity title. See docs/LAUNCHER.md:31-47, dist/pudl-launcher.js:7-45 and :127-166.

## Options

Costs below are relative engineering scope, not schedule estimates. Every visible change requires a generic mockup and approval before implementation. The existing launcher and menu-mode behavior must remain available in every option.

It couples menu generation to arbitrary panel structure and risks importing presentation controls. The host-owned command declarations are a better boundary. |
| Explicit launcher-tab ribbon content, recommended | Selecting the product tab shows Launcher, then the meaningful host actions such as Updates, Settings and Exit. Hamburger and the Launcher button open the catalog. | Add a documented, opt-in source for this tab's ribbon commands. Supply a single Launcher action when no row is declared. | Declare a small set of existing command IDs and their presentation in the shared host layer. It implements the proposed useful startup row without embedding a product-specific action list in PUDL. |
| One Launcher button | Selecting the product tab shows one Launcher button; its click opens the existing catalog with all header actions intact. | Synthesize that action for the launcher tab and make ribbon title activation select the row. Preserve menu/narrow opening and focus transfer into the launcher. | No new header-action mapping. Use existing launcher target, label and host interception. | Small. ## Recommendation

Use explicit launcher-tab ribbon content with a single Launcher action as the general fallback. The proposed initial row is Launcher plus the host's existing meaningful header commands. PUDL owns how the tab and ribbon behave; the host owns which commands exist and what they do. Selecting the identity in ribbon mode chooses the row, while the hamburger and explicit Launcher action open the catalog. Menu and collapsed modes keep their existing launcher activation. This behavior must be visible in the approval mockup because the identity currently opens the launcher immediately even in ribbon mode.

Keep header actions inside the launcher as well. Reuse registered commands and their current state rather than reparenting or copying header controls. Preserve focused-editor command targeting for ordinary ribbon actions. A Launcher action intentionally moves focus to search or browsing, using the launcher's public presentation API and the visible opener for return focus.

The proposed API should be additive and general to a host-level identity tab. Its exact attribute or descriptor shape is deferred until the visible behavior is chosen. It must preserve links, command ownership, disabled reasons, localization, updates and normal toolbar overflow. It must not export generated ribbon DOM or private item metadata as a host integration API.

## Evidence and later validation

The PUDL implementation engineer and independent verifier both performed read-only source/contract/test reviews. Neither ran a build, tests or a browser. The host lead supplied narrowly scoped code and install facts. No screenshot or customer-work description was retained in this record.

Current tests cover ordinary ribbon selection, return-to-applet selection and launcher popup/collapsed behavior separately. No focused test combines an empty initial launcher identity with ribbon mode. Existing generic samples/menu-ribbon.html and samples/host-launcher-tools.html, plus tests/fixtures/menubar-launcher.html, can inform an invented approval mockup. They are not already a validated combined solution.

After approval, validation must cover saved mode reload, deliberate remembered tab selection, no-front and front applets, application composition, async fill/clear, disabled-but-visible commands, narrow/RTL folding, keyboard selection and focus return, pinned launcher duplication and guarded host actions. The stock toggle's constant-label semantics should be kept explicit. Changing its words to an action label would be a separate localized UI decision.
